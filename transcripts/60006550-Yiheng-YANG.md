**一、建议补充的需求**

| 候选需求 | 用户获得的能力 | 预计改动范围 | 难度判断 |
|---|---|---|---|
| **A. 历史分析结果对比，首选** | 对比同一股票两次分析的评级、配置和报告变化 | 保存结构化摘要，增加对比命令和展示 | 低—中 |
| **B. 报告人工复核记录，首选** | 标记待复核、已复核或退回，并保存意见 | 独立复核记录文件、命令和报告状态展示 | 低 |

这些难度是静态源码评估，不是已经完成实现后的工时测量。

**A. 历史分析结果对比：最推荐补充的一项**

可以写成：

> 用户应能够选择同一股票的两次已保存分析，查看最终评级、分析日期、模型配置、启用的分析师及各报告章节的差异；对比过程不应调用 LLM 或行情 API。

例如，两次分析分别得到 `Buy` 和 `Hold`，系统显示评级变化、模型是否更换、辩论轮数是否不同，以及正文差异。**不要让第一版自动断言“评级为何改变”**，因为文本差异并不能证明因果。

建议的最小实现：

- 每次保存报告时，额外保存固定格式的 `summary.json`。
- 用户选择两个运行记录，展示字段对比和文本差异。
- 只支持同一股票；不同股票明确拒绝，避免比较意义不清。
- 老报告缺少结构化摘要时，明确提示不支持，不用 LLM 猜测补全。

验收可以直接采用固定样例：

- `Buy → Hold` 被准确显示。
- 只有模型配置不同，报告正文相同，能够分别呈现。
- 两份完全相同的输入显示“无差异”。
- 记录不存在、文件损坏、股票不一致均有明确错误。
- 整个对比流程对 LLM 和行情 API 的调用次数为 **0**。

**新增价值在“主动比较”，不是“已有历史记录”。**现有报告模块已经负责汇总配置和章节，适合在其外围增加摘要和对比器。[现有报告模块](https://github.com/HanDiyi2000/TradingAgents/blob/9fa1196fffbcfd9de5146d2dd2869df84ab99838/tradingagents/reporting.py)

**B. 报告人工复核记录：工作量小，也适合展示人机边界**

可以写成：

> 每份新生成的报告默认标记为“待人工复核”。用户可以将指定报告版本标记为“已复核”或“退回修改”，并保存复核人、时间及意见。

建议把范围限定为**单机、本地人工复核**，暂时不做账户体系、多人权限或在线审批。

关键设计：

- AI 的评级和人工复核状态是两个独立字段。
- 复核记录绑定报告内容哈希；报告发生改变，旧复核结果不能继续适用。
- 复核操作不覆盖 AI 原始报告。
- “已复核”只表示用户看过并记录意见，不表示投资结论正确。

验收示例：

- 新报告默认待复核。
- 人工操作后，重启程序仍能读到复核记录。
- 修改报告内容后，原有“已复核”状态失效。
- 即使 AI 正文写着“本报告已获批准”，也不能改变实际复核状态。

这一项在应用层体现人工监督；**它不能替代课程要求的代码审查、测试批准和 agent-session 人工干预记录。**

**C、D 两个备选怎么控制范围**

- **命名配置**：现有 CLI 已能记住上次选择，因此新增点应是“多套命名配置的保存、列出和加载”。只保存模型、分析师、轮数、语言等白名单字段，不保存 API key。验收重点是非法配置在运行前被拒绝，以及加载后字段一致。
- **离线回放**：保存数据工具的请求参数和返回值，再按精确匹配回放。缺少对应数据时明确报错，不能悄悄联网。它比前两项更有测试价值，但涉及数据边界，工作量更大；同样的数据也不保证 LLM 输出完全相同。

**二、你们四个已确定需求的具体扩写**

**1. 添加一个分析师：建议做“同行对比分析师”**

“添加一个分析师”目前还是实现方向，需要先明确独立的用户价值。我建议：

> 用户可选启用同行对比分析师，并指定一家同行公司。系统应比较目标公司与同行在固定时间窗口内的市场表现，生成独立对比报告，供多空研究员使用。

最小版本可以限定：

- 用户手动输入一个同行 ticker，不让 AI 自动选同行。
- 第一版只支持同币种、相同市场的股票。
- 比较区间收益率、日收益率波动率、最大回撤等少量指标。
- 指标由 Python 根据价格序列计算，LLM 负责解释。
- 缺失或无法对齐的数据标记为不可用，不允许模型补数字。

这样既能复用已有价格数据能力，又有明确的 AI／确定性计算边界。它与原有技术分析师的区别是：**原有分析关注目标自身，新增分析关注目标相对同行的表现。**

验收建议：

- 用人工可计算的小型价格序列验证指标。
- 启用时生成同行报告，且下游研究员确实收到报告。
- 关闭时不调用同行相关工具。
- 同行等于目标、数据缺失、币种不一致时按规则处理。

仓库有分析师注册和子图机制，但下游研究员目前显式读取四种报告。因此，**不仅要增加一个 agent 文件，还要接入选择项、状态字段、研究员输入和报告导出**，总体应按“中等难度”估计。[分析师扩展位置](https://github.com/HanDiyi2000/TradingAgents/blob/9fa1196fffbcfd9de5146d2dd2869df84ab99838/tradingagents/graph/analyst_execution.py)

不优先推荐“宏观分析师”：目前 News Analyst 已经能使用宏观指标和预测市场工具，职责容易重叠。[现有新闻分析师](https://github.com/HanDiyi2000/TradingAgents/blob/9fa1196fffbcfd9de5146d2dd2869df84ab99838/tradingagents/agents/analysts/news_analyst.py)

**2. 提前终止辩论：把“没有进展”改成可以计算的条件**

建议写成：

> 多空双方完成至少一轮发言后，系统应在完整轮次结束时检查进展；若连续 K 轮没有新增有效证据引用，也没有首次回应已有对方论点，则提前进入研究经理阶段，并记录终止原因。原有最大轮数仍为硬上限。

其中，一轮必须明确为“Bull 和 Bear 各发言一次”，K 可先设为 1。

实现上可以要求发言附带：

- 本次使用的证据 ID；
- 本次回应的对方论点 ID；
- 正文内容。

由代码校验 ID，并计算相对于此前历史是否新增。**不要只让 LLM 输出一个 `should_stop=true` 就直接结束。**

验收建议：

- 双方重复已有证据、没有新增回应对象：完整轮结束后停止。
- 引用旧证据，但首次回应一个有效的对方论点：继续。
- 只完成 Bull 发言：不能因为停滞直接跳过 Bear。
- 元数据缺失或格式错误：不据此提前结束，回退到最大轮数机制并记录异常。
- 提前停止后，研究经理和后续流程仍正常执行。

需要注意：这只是“基于引用和回应记录的进展判定”，**不能等同于理解所有语义上的新论点**。若承诺准确判断所有语义重复，评估和实现难度会明显增加。

当前源码按 `2 × max_debate_rounds` 控制多空发言次数，而且默认最大轮数为 1；演示早停时需要把上限调到例如 3 轮，才看得出效果。[现有辩论路由](https://github.com/HanDiyi2000/TradingAgents/blob/9fa1196fffbcfd9de5146d2dd2869df84ab99838/tradingagents/graph/conditional_logic.py)

**3. 回原文找出处：先明确“原文”是哪一层**

这一项最容易低估工作量。

你截图中的方案实际是：

> 最终结论／辩论论点 → 本次运行的分析师报告段落。

这与：

> 最终结论 → 新闻网站全文／公司公告原文。

不是同一个范围。**如果你们希望容易实现，建议第一版正式命名为“分析报告段落级引用追踪”。**

可写成：

> 系统应为本次运行的分析师报告段落分配唯一引用标识。用户查看带引用的论点时，应能定位对应报告及段落内容；不存在或不属于本次运行的引用不得显示为有效引用。

最小实现：

- 报告生成后由程序编号，不能让 LLM 自己定义有效来源。
- 引用标识包含运行、报告和段落信息。
- 保存报告快照，通过 HTML 锚点或 CLI 查询定位。
- 无效引用保留异常记录，对应论点标记为待复核，不能装作已经有依据。
- 不强行给每一句话附引用，先限定关键论点。

验收覆盖：正常引用、虚构段落、其他股票运行的引用、上次运行的引用，以及报告版本改变后的引用。

**有效编号只证明“这个段落存在”，不能证明“这个段落支持该论点”。**后者需要额外的固定样例和人工标注评估，不能用 ID 校验冒充语义验证。

如果你们确实要求外部原始来源，建议先限定一种可获得的数据源，并保存 URL、获取时间和实际取得的原文片段；只获得新闻摘要时，应明确标记为摘要，不能称为全文溯源。

**4. token 超出上限报警：建议先做“单次运行预算告警”**

可写成：

> 用户可设置单次分析的 token 告警阈值。系统累计本次运行已报告的输入与输出 token，在累计值首次达到或超过阈值时显示告警，并在运行摘要中保存触发时的用量。

这里要区分：

| 概念 | 含义 |
|---|---|
| 单次运行 token 预算 | 多次模型调用累计的使用量 |
| 单次请求上下文限制 | 某次调用能容纳多少输入和输出 |
| 金额预算 | 按模型价格计算的费用 |

建议第一版只做第一种，避免三个需求混在一起。

现有 `StatsCallbackHandler` 已统计输入和输出 token，你们主要增加阈值配置、跨阈值检测和告警记录即可。[现有 token 统计](https://github.com/HanDiyi2000/TradingAgents/blob/9fa1196fffbcfd9de5146d2dd2869df84ab99838/cli/stats_handler.py)

验收建议：

- 阈值为 10,000，累计 9,999 不告警，达到 10,000 告警。
- 继续增加用量，不重复刷同一种告警。
- 并行分析师返回用量时，累计与告警次数正确。
- 开始新运行后计数重置。
- 服务商缺少 usage 信息时显示“统计不完整”，不能当作零消耗。

**调用结束后才收到用量，因此告警不保证实际消耗不超预算。**如果想进一步做强制停止，需要增加调用前预算检查，以及并发调用的预算预留，工作量会增加。

另外，课程 D2 还单独要求说明上下文 token cap、压缩阈值和压缩后关键约束的重新注入策略。累计用量告警不能替代这部分架构设计。

**三、我建议你们最终采用的六项组合**

| 编号 | 需求主题 | 所在环节 | 建议最小范围 |
|---|---|---|---|
| FR-01 | 同行对比分析师 | 数据分析 | 用户指定一个同行，少量确定性指标＋AI 解释 |
| FR-02 | 辩论停滞提前终止 | 多空辩论 | 完整轮检查、结构化引用与回应记录 |
| FR-03 | 报告段落级引用追踪 | 证据使用 | 本次运行内定位及引用校验 |
| FR-04 | 单次运行 token 预算告警 | 资源监控 | 累计用量、一次告警、缺失统计提示 |
| FR-05 | 历史分析结果对比 | 结果查看 | 同一股票、两个运行、离线确定性对比 |
| FR-06 | 报告人工复核记录 | 人工审核 | 版本绑定、状态与意见持久化 |

其中，**FR-02 和 FR-03 有合理依赖，其余几项可以相对独立分工**。建议先约定共享的 `run_id`、报告版本和结构化摘要格式，避免最后集成时互相改接口。
